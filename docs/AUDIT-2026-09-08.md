# Independent audit of ai-rimworld 0.3.0 — 8 September 2026

## Verdict

The side conversation delivered a substantial support-system release, but its checked-off remediation list is stronger than the evidence supports. Five defects remain reproducible offline. Most urgently, the routine continuation monitor is incompatible with the captured RimMolt catalog. Treat 0.3.0 as requiring repairs and field qualification before using unattended continuation.

This audit inspected the installed source and release records; it did not recover the ephemeral conversation's final prose response. It made no game calls, changed no game state, and applied no source fixes. The accompanying scripts use temporary synthetic campaigns or read previously saved responses.

## Findings

### A01 — P1: The continuation template and coverage checker use an invalid pawn category

Locations: [template](../templates/continuation.json), [monitor.py](../tools/rimworld/monitor.py), lines 65–66 and 95–106; [test_monitor.py](../tests/test_monitor.py), lines 24–28 and 40–49.

The captured RimMolt list_things schema enumerates lowercase `pawn`; the template submits `Pawn`. The runner's own validator rejects it with `$.category: value is outside enum.` Correcting the plan alone does not solve this: coverage still searches exclusively for `Pawn`, rejecting a valid lowercase observation as missing coverage. The independent probe reproduces both failures.

There is a second response-shape mismatch in this same path. Coverage requires an explicit `hostile` field on every pawn, while the captured tool description says compact responses omit false values. The template does not request `verbose:true`. The synthetic test catalog omits the category enum and its safe response explicitly includes `hostile:false`, concealing both incompatibilities.

Impact: the advertised routine loop cannot pass this path against the captured API. It fails closed, so this is an availability and agent-loop defect rather than evidence of unsafe time advancement.

Repair: reconcile the template and coverage with the actual schema and documented compact/full shapes; require demonstrably complete map coverage. Add offline integration fixtures taken from the captured catalog and responses. Then qualify against the current live catalog during an authorized game-control session; the captured catalog is historical evidence, not proof of today's server state.

### A02 — P2: Projection cost still grows with every distinct query scope

Location: [memory.py](../tools/rimworld/memory.py), lines 122–148 and 477–521; [benchmark.py](../tools/benchmark.py).

Using all response-affecting arguments for identity correctly prevents query collisions. However, the projection retains the full latest payload for every unique query key, then deep-copies and rewrites that entire set on ingestion. Moving area queries accumulate rather than remaining a bounded current working set.

Independent comparison, 250 observations per campaign with 40 item rows per response:

| Workload | First 25 median | Last 25 median | Final projection | Distinct scopes |
| --- | ---: | ---: | ---: | ---: |
| Same query scope | 3.10 ms | 2.97 ms | 7,246 bytes | 1 |
| Changing query coordinates | 6.98 ms | 75.26 ms | 1,719,767 bytes | 250 |

This measures local processing, not total gameplay latency. It nevertheless exposes a growth dimension absent from the release's 5,000 repeated-status benchmark. The latter genuinely remains stable and reproduced independently at 2.42→2.46 ms, but does not establish scalable varied-query play.

Repair: preserve full immutable evidence and indexes, while separating historical query results from the current working projection. Define retention and revalidation semantics that preserve unresolved threats, dependencies and uncertainty. Benchmark mixed queries, pawn turnover and action scopes before claiming the growth problem resolved. Do not simply discard old risks to reduce size.

### A03 — P2: Unchanged medical observations can be larger than the original payload

Locations: [safety.py](../tools/rimworld/safety.py), lines 54–61; [observations.py](../tools/rimworld/observations.py), lines 235–245.

`health_conditions` embeds virtually the entire health response as a risk value. The delta formatter reattaches all risks even when no fields changed. A saved actual health response serialized to 2,591 bytes; an unchanged delta serialized to 5,306 bytes in the independent probe. This measurement includes the formatter's metadata and risk output. It is not a claim that every healthy-pawn response doubles.

Impact: repeated medical reads can consume more working context despite the new delta path. The original medical-visibility fix is valuable, but its representation conflicts with compact routine observations.

Repair: retain a stable, compact risk identity, exact decision-relevant medical values and evidence pointers; return changed details once. Keep full conditions retrievable before medical or combat decisions. Test stable injuries and changed bleeding/infection alongside empty-health fixtures.

### A04 — P2: A typed review deadline can pass without becoming due

Locations: [memory.py](../tools/rimworld/memory.py), lines 197–206 and 292–310; [safety.py](../tools/rimworld/safety.py), lines 123–135.

Issue creation accepts `deadline.kind = review`. However, issue review scheduling uses only `revisit_tick`, and the deadline collector consumes only hard deadlines. A review deadline at the current tick, with no duplicate revisit_tick, yields `soft_reviews: []`. Its deadline remains stored, but is not delivered through the due-review mechanism used by continuation.

Impact: the monitor can miss an intended strategic or maintenance review. Hard deadlines are a separate path and are not implicated by this reproduction.

Repair: make the supported typed review deadline participate in review scheduling, with explicit unknown-clock behavior. Add before/at/after deadline cases and a continuation-stop regression.

### A05 — P2: Rebuild does not restore a missing action index

Location: [memory.py](../tools/rimworld/memory.py), lines 150–170 and 465–469.

The action-index writer only processes journal records after the active-action cache offset. `rebuild()` rebuilds observations, but leaves that offset in place. In a temporary campaign, creating an action, removing its derived index file and calling rebuild leaves `action_record(id)` returning null, although the authoritative action journal still contains the record.

Impact: missing derived files can make recorded work unavailable through indexed lookup after a purported successful rebuild. This falls short of the release's rebuildable-index claim; it does not demonstrate loss of the original journal.

Repair: explicitly rebuild action indexes and caches from their authoritative journal during recovery, or reconstruct missing entries on demand. Test missing individual indexes with intact caches, closed actions, and interrupted derived writes. Never repair this by rewriting or rolling back original action history.

## What the side conversation actually added

Compared with the preserved 0.2.0 archive, the installed release adds safety, outcome-contract, continuity and monitor modules, plus audit/monitor regression suites and a benchmark. It changes the MCP client, controller, memory, observations, run management, learning, history, metrics, CLI, templates and operating documentation.

The main improvements are:

- Run-local learning with explicit shared promotion and pinned shared adoptions.
- Richer observation identity, freshness, partial-response handling and evidence provenance.
- Stronger action-outcome verification and explicit same-game reconnect reconciliation.
- Immutable handoffs with strategy, unresolved work, evidence versions and learning references.
- Grouped observations, outcome contracts, risk acknowledgements and typed deadlines.
- Finite routine continuation with a separate pause guardian and interruption records.
- Telemetry, indexed retrieval, incremental journal folds and stronger screenshot/chapter integrity checks.

These are implemented mechanisms, not merely a plan. Their positive value does not establish live compatibility, improved decision quality or faster play. In particular, the original medical/context/index/monitor remediation claims need narrowing or reopening in light of A01–A05.

## Recommended repair and validation order

1. Fix A01 and add actual-schema/response-shape fixtures before qualifying continuation.
2. Fix A04 and A05 so reviews and continuity survive normal scheduling and derived-file recovery.
3. Fix A03 incrementally; retain medical evidence and unresolved risks while reducing duplication.
4. Address A02 with a measured current-view design, keeping immutable history. Avoid an unrelated tooling rewrite.
5. Re-run offline checks, then perform a separately authorized live-control qualification: finite waits, actual pause confirmation, real guardian process loss, medical/threat coverage and reconnect behavior. Measure agent-to-game delay and false interruptions under routine, combat and recovery workloads.

Not run during this audit: live MCP/UI tests, real guardian scheduling/failure experiments, new-game/resume play, actual screenshot capture, a real five-day chapter, or end-to-end gameplay timing. These would interact with the live run and remain unverified. The separate demo command was not rerun; the published demo is evidence from the prior implementation, not a new audit result. No win-rate improvement or legitimate victory is established by this release audit.
