### Trade phase — the open question is now answered

**VERIFIED: `set_trade` cannot batch today, and the exception is safe to extend.**
An `independent:true` batch of three sells stopped after action 0 with
`completed:1, not_run:[1,2], reason:"Action response requires review"`. The receipt that
caused the stop was `ok:true`, `transfer:-35`, `silverAfterDeal:242`, and its ONLY review
signal was `_dialogOpen:true` — structurally identical to the `window_action` receipts the
same-dialog exception already allows through. This is the live evidence the plan deferred.
Recommendation: extend `expected_same_dialog` to `set_trade` while `list_trade` reports the
same active trader and negotiator, and add `trade_action` accept as an explicit batch
terminator that always stops.

silver is reported separately in the `silver` field. `returned 57 / tradeableCount 58` is the
honest signal and `rows_withheld` explains it correctly. Benign upstream behavior, not a bug.

**New friction — annotations do not reach `rw_observe` sections.** `rows_withheld`,

`rw_read`/`rw_act` path uses. The same `list_trade` read inside an `rw_observe` section shows
the 57/58 gap with no explanation. The annotation belongs in the composition path too.

**Fix confirmed working #4 — event context scoping.** A wait during the standing berserk

### Time-advancement friction (the biggest decision-loop cost found)

**A modal dialog silently froze time and `rw_wait` never said so.** Three consecutive waits
returned `ok`, `cause:forcePaused`, `ticksWaited:0`, with the game tick unchanged at 3770419.
Nothing named the blocker. It was a "Research finished: Deep drilling" `Dialog_NodeTree` with
`forcePause:true`. I only found it by calling `list_windows` myself. Three model round trips
bought zero game time. Fix: when a wait returns `ticksWaited:0` with `forcePaused`, read the
pausing window and name it plus the `window_action` that clears it.

**The server's 2500-tick crisis cap is invisible.** Every wait requesting `maxGameTicks:20000`
returned `ticksWaited:~2502, cause:"timeout"`. The upstream `wait_for_event` schema documents
it — waits are capped to one in-game hour while hostiles are present, fire is in the home
area, or a colonist has a life-threatening condition, and `force:true` bypasses it. But the
response carries no signal: `wait_budget` was null and `cause:"timeout"` reads as "nothing
happened", not "your horizon was cut by 8x". Skipping a quiet day costs 24 calls instead of 3.
Fix: when `ticksWaited` is far below the requested tick budget and cause is timeout, say the
crisis cap likely applied, name the condition, and name `force`. Do not auto-force.

**`context:"brief"` measured.** Waits came back at 3,800-6,000 bytes against the recorded
16,722 median. Over the 22 waits in this session that is a large saving, and I never once
wanted the omitted sweep because I was choosing `verify` deliberately.

**Host command timeout vs the game lock.** A wait loop exceeding the 120s shell timeout gets
backgrounded while still holding `operation.lock`, so no other call can run until it exits.
Workable, but nothing documents it. Long loops should be started in the background on purpose.

### Colony crisis: what the tools did and did not surface

The real cause of two colonists dying was **two passive coolers running inside the barracks
during a cold snap**, which ISSUES.md had flagged as an open question since the previous
session. The chain that found it: `get_room` reported the barracks at 5.5C (the friction
report was right that `get_conditions` is outdoor-only and `get_room` is the indoor tool);
`get_area` with `layer:buildings` and ascii render put `"m": "passive cooler - 2 in view"` in
the legend; `list_things defName=PassiveCooler` gave both exact ids. That is a good tool chain
and it worked. `inspect_thing` then showed the only available action is Deconstruct, so there
is no off switch.

**`list_things` with a defName filter is dramatically better than radius+limit.** My
`nearId` + `radius:12` + `limit:60` read silently hit the limit and returned zero coolers;
`defName:'PassiveCooler'` returned both instantly with `matched:2`. The limit truncation was
reported, but a caller scanning for a label would just conclude the thing is not there.

**A bad thing id blocks an entire composition.** `inspect_thing` on `Campfire169350`, a
campfire that no longer exists, returned an upstream error, which is correctly blocking, and
the two pawn reads after it were `not_run`. Arguably an unknown-id error is also complete and
self-describing and could join the recoverable class. Leaving that judgement open.

**Placement worked first try.** Reading the `get_area` ascii grid, deriving that row 0 is
maxZ, and cross-checking against the known cooler coordinates let me place the campfire at
129,120 with no failed ghosts. The `placement.interactionCell` machinery never had to fire.
The build_structure workflow note is still right; it just was not needed this time.

**Ward, the Medicine 14 doctor, was meditating at a wooden wall while two colonists froze.**
No alert connects "colonist needs treatment" to "your doctor is idle on a non-work activity".
Not a tooling defect, but a decision the packet could surface: the medical facet lists who
needs care and never lists who could provide it.

**`force` was deliberately not used.** The 2500-tick cap was active the whole time because a
colonist had a life-threatening condition. The docs say use it according to actual risk and
never automatically; with two people dying of hypothermia that test was easy to apply.

### Ranked fix list coming out of this playtest

1. A wait returning `ticksWaited:0` with `forcePaused` must name the blocking window and the
   `window_action` that clears it. Cost three dead round trips.
2. A wait cut far below its requested tick budget must say the crisis cap applied and name
   `force`. Cost roughly 8x the calls to cross quiet time.
3. `truncated` that merely honors the caller's own `limit` must not be classified as degraded.
   Affects the decision `threat` topic on every busy map.
4. Extend the same-dialog batch exception to `set_trade`. Now verified live: the receipt is
   `ok:true` with `_dialogOpen` as its only review signal, identical to `window_action`.
5. Correct the trade workflow: confirm bought goods with `list_things category=item nearId=
   <trader>`, not `list_unmanaged_items`, which matched 1123 rows with no positional filter.
6. Run receipt annotations (`rows_withheld`, `already_satisfied`, `retry`, `deal`) in the
   composition path too, not only `rw_read`/`rw_act`.
7. Materialize decision presets inside `rw_wait verify`, or reject them there with a clear
   message, instead of silently returning the raw status bundle.
8. Let a wait ignore notification classes that cannot change a decision. A cold snap emitted
   one wait-ending notification per dying plant; one wait advanced 58 ticks.
9. Dedupe `_threatWarning` across one-shot CLI calls, or drop it from receipts by default. The
   `same_as` machinery is connection-scoped and one-shot CLI is the documented default, so it
   never fires and every receipt pays about 500 bytes.
10. Give `list_things` pawn rows a weapon field, so the friendly-fire rule can be applied from
    the roster instead of one `get_pawn` per candidate.
11. Say why `order_pawn` returned `options: []` (target in a mental state, asleep, unreachable).
